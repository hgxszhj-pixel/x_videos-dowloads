## 0. 一句话结论

Anthropic 把「人逐行审代码」换成**七层叠网**（他们自称 "cheese slices"——每层有洞，叠起来错误很难对齐）：

> 提交前自测 → CI → AI 多智能体审查（+ 投票过滤）→ 独立安全审查
> → 风险分级人工批准 → 合并队列 + 灰度发布 → 快速回滚

结果：**约 90% 的代码由 Claude 写**，6→9 月合并 PR 数翻倍以上，**回滚率反而降了 40%+**。

---

## 1. 关键数据（Anthropic 自报，无第三方验证）

| 指标 | 变化 |
|---|---|
| Claude 写的代码占比 | ~90% |
| 单体仓库日均变更量 | 5 月 ~2500 → 9 月 >30000 |
| 6→9 月合并 PR 数 | 翻倍以上 |
| **回滚率** | **降 40%+** |
| 带实质审查意见的 PR 占比 | 16% → 54% |
| 一次过审率 | 65% → 78% |
| 需要 5 轮以上审查的 PR | 8.9% → 1.5% |
| 平均审查轮次 | 2.08 → 1.32 |

> 视频里点名的两个数：**PR 翻倍 + 回滚率降 40%**——这就是整套流程的 KPI。
> 「回滚率」而不是「审查通过率」作为北极星，是这套设计最值得抄的一点。

## 2. 七层流程（视频自己的分段导航）

### ① 开篇综述
AI 写代码越来越快，人工逐行审查跟不上；Anthropic 的应对是上面那套七层流程。

### ② 提交前：开发环境验证 + 本机 code review（视频第一个重点，56–154 s）

两件事：

1. **验证功能是否真的做完了**——把功能跑起来给 agent 看：
   网页类让它用**浏览器访问**；有 UI 的**给截图当参考**让它对照检查实际效果。
2. **换一个全新上下文的 agent 审代码**——把「需求 + 代码改动」交给**另一个**智能体。

> **为什么要换新的 agent**（视频原话大意）：
> 写代码的 agent **保留着之前的推理和对话**，回头检查时可能**还是沿着原来的思路走**，会漏掉同样的问题；
> 一个**全新上下文**的智能体才能给出**独立的第二意见**。
> 也可以换模型交叉审，但**换模型不等于一定审得更好**——所以实践中常用「不同模型 / 不同 AI 工具」交叉。

对应 Anthropic 原文：PR 前用 **fresh-context subagent** 拿 diff 对照 `CLAUDE.md` 和 `REVIEW.md` 再审一遍。

### ③ CI 检查（154–222 s）
提交 PR 后自动跑项目预配置的检查：业务测试（无优惠券、多个优惠券叠加…）、能否编译、
常见代码问题、能否打包。**结果显示在 PR 页面；必检项失败就按错误信息改完重提，通过才能往下走。**

### ④ AI 审查（222–490 s）——本视频篇幅最大、含金量最高

**输入三件套**：PR 描述（想做什么）+ 具体代码变更 + **整个仓库的上下文**。

**审查的几个方面**：
- 这次的改动**有没有解决问题**
- 是否**适合现有系统**、会不会影响其他功能
- 修 bug 的话，有没有**找到根本原因**
- 例：改了订单金额算法 → 不只看算得对不对，还要看优惠券与折扣的**计算顺序**是否符合既有规则、
  改了这个公共方法会不会**影响退款金额的计算**

**问题不会直接抛给开发者**，中间还有一道过滤：
- 第一组智能体对**每条问题做验证和投票**，足够多 agent 认为问题确实存在，才发布这条审查意见
- 过滤规则：**纯代码风格、诊断提示、代码清理类**意见直接丢掉
- 剩下的意见按严重程度排序，标为 **重要问题 / 小问题 / 原有问题**
  - 「原有问题」≠ 不严重，而是**这次 PR 之前就存在**——避免把旧账算到这次改动头上

**每个问题都要作者回复**：确实有问题就修；认为是误报或有意不改就**说明理由**并标为已解决。
**缺陷审查或安全审查中只要还有未解决的发现项，这个 PR 就不能合并。**

### ⑤ 安全审核（490–570 s）——独立一道闸，能阻断合并

五类常见漏洞模式：

1. **SQL 注入**——用户输入直接拼进数据库查询语句
2. **跨站脚本 XSS**——用户提交内容直接显示在网页上，没有适当处理
3. **身份验证与权限控制**——订单接口只检查「有没有登录」，没检查「订单是不是属于这个用户」
4. **不安全的数据处理**——后端没验证输入，直接采信前端传来的价格/优惠金额，用户可篡改订单应付金额
5. **第三方依赖中的已知漏洞**——框架和第三方包本身可能引用安全问题

团队可按项目要求调检查规则和严格程度。**有未解决的安全发现项就不能合并。**

### ⑥ 人工批准（570–660 s）——按风险分级，不是所有人都要看

风险由**分类器**判定（不是作者自评）：

| 风险档 | 例子 | 人工批准人数 |
|---|---|---|
| 低 | 文档、文案、仅内部使用的功能 | **0 人**（自动审查 + 安全检查过了就行） |
| 中 | 普通产品功能变更、缓存等敏感区域 | 1 人 |
| 高 | 计费、自动更新、CI 工作流等 | 2 人 |

**Agent 的批准永远不计入人工名额。**

### ⑦ 合并队列 + 上线发布（660–901 s）

- **合并队列**：后面的 PR 基于更新后的主分支**重新接受检查**（不是直接叠上去）
- **上线发布**：分阶段、两个通道（内部 → latest → stable），配 feature flag，**出问题能一键回滚**，还有每周 on-call 轮值
- **上线前五个问题**（人必须亲自回答，AI 不接管）：
  1. **值不值得做**（决定要不要做这件事）
  2. **高风险代码**（例：金额 = 总价 − 优惠 + 运费 → 要校验**计算顺序**与**金额精度**）
  3. **架构设计**
  4. **验证证据**（证据在哪，验没验过）
  5. **对结果负责**

## 3. 三个控环手段——本机最值钱的部分（视频「第一招/第二招/第三招」）

这是视频最实用的一段：**AI 审查最常见的失败模式是「审查 → 改 → 再审」无限循环**。
Anthropic 有个 PR 一晚上跑了 50+ 轮，`git blame` 显示 **约 59% 被反复标记的代码从第 1 轮就存在**——
即：agent 在反复挑**早就存在**的问题，不是新引入的。

三个控环手段：

| 招 | 做法 | 为什么有效 |
|---|---|---|
| **① 轮次上限** | 来回 **3 轮**还没通过就**先停一停、重新想方案**（**不是自动放行**） | 3 轮还在打补丁，说明方案本身错了，继续打补丁是浪费 |
| **② 逐步缩小复审范围** | 前几轮结合整个项目全面查；后面只重点查**新增的 diff** + 相关调用 | 已审过的内容不重复审，就不会反复挖出旧问题 |
| **③ 意见一次说清** | 发现一处 `double` 精度风险，就让作者**一起排查所有同类金额问题**；**已提出并处理过的问题不每轮重发** | 避免「这轮改一处、下轮又冒一处」；避免让作者反复回应 |

> 视频给了具体例子：订单金额的「优惠券 + 满减」叠加，AI 连改三轮还是不对 →
> 此时该停，**重新确认优惠到底按什么顺序计算**，而不是继续在错的思路上打补丁。

## 4. 与本机 `code-review-canonical` 的差距对照

本机 skill：`~/.claude/skills/code-review-canonical/`（`SKILL.md` + `code-reviewer.md`）
本机 repo 已有：`docs/dna/review-checklist.md`（5 阶段 pre-merge 清单）、
`scripts/mutation_smoke.sh`（变异测试）、`scripts/track_quality.sh`、commit-msg 7 门。

| 视频/Anthropic 的做法 | 本机现状 | 处理 |
|---|---|---|
| **仓库上下文是审查的正式输入**（对照 `CLAUDE.md` / `REVIEW.md`） | reviewer 只拿到 DESCRIPTION / PLAN / SHA，**拿不到仓库约定** | ✅ **已补**：`{REPO_CONTEXT}` 槽位 + 「Repo fit」检查项 |
| **原有问题 vs 本次引入** | Critical/Important/Minor 三档，**没有「旧账」分类** → 老代码的锅算到新改动头上 | ✅ **已补**：「Attribution」检查项 + 输出格式里的 introduced/pre-existing 标注 + DON'T 清单 |
| **同类问题一次说清 + 已处理不再重发** | reviewer 一趟输出，问题可能同类重复罗列 | ✅ **已补**：输出格式要求同根因合并成一条；DON'T 清单禁止重提已处理项；SKILL.md 加「Carry forward what was already raised」 |
| **轮次上限 3 + 缩小复审范围** | 无上限，可无限循环 | ✅ **已补**：`SKILL.md` 新增「Controlling the review loop」三条 |
| **多智能体并行 + 投票过滤** | 单个 reviewer subagent，且模板**明确禁止** reviewer 再派 subagent | ❌ **明确不抄**（见 §6） |
| **独立安全审查闸（5 类漏洞）阻断合并** | 全局 `common/security.md` + `security-reviewer` agent 已覆盖同类清单 | ⚠️ 已覆盖，不重复写进 prompt（Rule 6 减法） |
| **风险分级人工批准（0/1/2 人）** | 单人项目，无此流程 | ❌ 不抄（过度工程） |
| **合并队列 + rebase 后重检** | 本机单人分支流 | ⬜ 可选，未动 |
| **回滚率作为北极星指标** | `scripts/eval_trace.py` 有 4 指标（success_rate / avg_total_ms / resolver_chain_length / stall_count），**没有「回退/逃逸率」** | ⬜ 可选：加一个 `revert_rate` 指标 |
| **历史事故 PR 变成每日 eval 集，改 prompt 必须先过分数** | 本机有 `mutation_smoke.sh` + `criteria` skill（H1–H9），**但没有「改审查 prompt 必须先跑分」的门禁** | ⬜ 可选：这是视频之外最值得抄的一条 |
| **PR 前用全新上下文的 agent 再审一遍** | 本机 skill **已经是这个设计**（「never your session's history」） | ✅ 早就领先，不用改 |

## 5. 已落地的改动（2026-10-30）

`~/.claude/skills/code-review-canonical/code-reviewer.md`
- 新增 `## Repository Context` 段 + `{REPO_CONTEXT}` 占位符
- 新增 **Repo fit** 检查项（是否遵守仓库约定 / 是否绕开既有架构 / 是否复用既有模块）
- 新增 **Attribution** 检查项（本次引入 vs BASE 已存在；旧问题报一次、标注、不占审查注意力）
- 输出格式：每条问题必须标 **introduced / pre-existing**；同根因问题**合并成一条**
- DON'T 清单加两条：不把 BASE 之前就有的代码算到这次改动头上；不重提作者已处理的问题

`~/.claude/skills/code-review-canonical/SKILL.md`
- 占位符表加 `{REPO_CONTEXT}`，并说明「没有它 reviewer 就说不准『这个改动绕开了既有 X』」
- 新增 **Controlling the review loop**：轮次上限 3（不自动放行）、逐轮缩小复审范围、
  把已提出的问题带到下一轮

## 6. 明确**不**抄的三条（附理由）

1. **多智能体并行 + 投票过滤**
   视频的做法是多 agent 并行审查、再由投票 agent 过滤误报。本机 `code-reviewer.md` 里
   明确写了「reviewer 不得再派 subagent——每个 seat 已经有，重复派是纯浪费」。
   本机是单人项目、已有 7 门 commit-msg 门禁 + 变异测试 + `criteria`，
   **投票的边际收益低于 token 成本**。等价效果用三个便宜手段拿到：
   归因分类（旧账不扣在新改动头上）+ 同类合并 + 不重提——这三条过滤掉的正是投票要过滤的东西。

2. **风险分级人工批准（0/1/2 人）**
   单人项目没有「需要几个人批准」这个维度，加了是空转。

3. **安全清单搬进 reviewer prompt**
   全局 `common/security.md` 与 `security-reviewer` agent 已经覆盖同类内容，
   在 prompt 里再抄一遍只是稀释注意力（Rule 6：提示词层是减法）。

## 7. 可选后续（本机尚未做，按性价比排序）

1. **改审查 prompt 必须先跑分**——把历史「本来会出事」的改动做成固定 eval 集，
   任何 prompt / 模型 / 工具改动先过分数再合入。对应本机 `mutation_smoke.sh` 的思路，
   但对象是**审查质量**而不是测试有效性。
2. **给 `scripts/eval_trace.py` 加 `revert_rate` 指标**——把「回滚率」这个北极星搬过来：
   现在是发版后人工回退多少条改动。
3. **合并队列语义**——本机若并行开多个 PR，合并前按更新后的 main 重跑一次检查。
4. **CI 场景补测**——视频提到「优惠券叠加」这类边界必须写成测试而不是靠人想。
