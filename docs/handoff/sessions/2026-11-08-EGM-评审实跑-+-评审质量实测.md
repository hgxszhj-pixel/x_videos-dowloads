## 实跑方式（含一个必须说清的限制）

`/egm:egm-review` **本会话不可用**——plugin 的 skill/agent 列表在会话启动时生成，本会话早于安装：

```
Skill(egm:egm-review) → Unknown skill: egm:egm-review
```

⇒ 走 SKILL.md 明确记载的 fallback：**手工执行 workflow + `general-purpose` subagent 先读人格文件**。

⚠️ **这意味着本轮验证的是 EGM 的「方法」，不是它的「插件适配器」。**
适配器侧（`omitClaudeMd: true` + `tools: [Read, Grep, Glob]`）本轮**完全没被走到**——
我用的是手写 prompt + `general-purpose`，隔离靠我的 prompt 设计，不靠插件机制。
适配器确实存在且配置正确（8 个 reviewer adapter 全带 `omitClaudeMd: true`；synthesizer 给 `Agent`+`Write` 且**不带** `omitClaudeMd`），
但**未实测**。⇒ 下次要验适配器路径，必须**新开一个 session**（安装之后）再跑。

## EGM 自身暴露的问题

1. **评审者会被仓库树里的「评分物料」污染 —— 这是真实风险，不是理论风险。**
   S9 的 `egm-style` 视角做全仓 grep 时**命中并读了我的答案键**（文件标着「评审方不可见」）。
   它**主动披露**并请求打折；S9 synthesizer **没有读**该文件，把它**隔离**（不合并、不丢弃）、
   并给出修复建议：把答案键放到仓库树外。
   ⇒ **实操规则：任何评测/答案/基准物料必须放在仓库树之外。** 本轮已把答案键挪到 `~/.egm-benchmark/`。
   ⇒ EGM 的隔离是「无对话历史」，**不是**「无仓库读取」——视角会 grep，而 grep 什么就拿到什么。
2. **SKILL.md 对 Stage 8/9 的标准映射不全。** 权威的 `docs/designs/review.md` 比 SKILL.md 多两条：
   Stage 7 还要用 `heilmeier-standard.md`、Stage 9 还要用 `re-implementation-standard.md`。
   只读 SKILL.md 的人会把 Stage 9 少跑一条标准。
3. **中途安装的插件当会话不可用**（`Unknown skill`），只能走 fallback 路径 ⇒ 首次安装后**必须新开会话**才用得上原生命令。
4. **成本 ≈ 44 万 token / 5 个 stage**，对一份 82 行文档。EGM 自己的 CLAUDE.md 定位「重」是对的。
