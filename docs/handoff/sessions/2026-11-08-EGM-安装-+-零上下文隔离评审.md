## EGM 是什么

**规范驱动开发（SDD）+ 双角色评审**：

- **Elephant（象）**：带完整项目上下文的 agent —— 探索需求、起草规范。
- **Goldfish（金鱼）**：**零对话历史**的独立 subagent —— 只看文档 + 被引用的源码，不看之前的讨论。
- **人**：做架构权衡、拍板。

核心命题写在 `docs/designs/architecture.md` 的 *Alternatives Considered* 里：**同一个会话里顺序跑评审会被自己的错误结论污染**（confirmation bias + context degradation），所以必须换干净的上下文来审。

四个子系统：`skills/`（7 个）、`agents/`（10 个人格）、`resources/document_standards/`（评审 rubric）、`docs/`。

5 阶段流水线：Brainstorm → Draft → Review(5 阶段 / 8+ reviewer) → Resolve → Implement + Drift 监控。

## Token 成本：实测推翻了我自己的顾虑

从 17 个文件的真实 frontmatter 量（不是估）：

| 组 | 条数 | 字符 | token（3.0–3.6 char/tok） |
|----|------|------|------------------------|
| skills | 7 | 1837 | 510 – 612 |
| agents | 10 | 1717 | 477 – 572 |
| **合计** | **17** | **3554** | **≈ 510 – 1185 / session** |

对照本机 2026-10-27 的实测口径：`rules/` 层 ≈ **9.1k token/session**，整个 trim 后的 skill 集 ≈ **1145 token**。
⇒ EGM 的常驻开销**与既有 skill 集同量级**，远低于 `rules/` 层 —— **不是问题**。

> 我在安装前把「装 17 个条目」列为主要反对理由。量完发现这理由站不住，**据实推翻**。

## 落地动作

```bash
claude plugin marketplace add google/elephant-goldfish-model   # ✔ marketplace: egm
claude plugin install egm@egm                                   # ✔ egm@egm v0.1.1, user scope, enabled
```

安装位置：`~/.claude/plugins/marketplaces/egm/`（skills + agents）与 `~/.claude/plugins/cache/egm/egm/`。
10 个 persona 的 frontmatter `name` 与 skill 里点名调用的**完全对得上**（`egm-zoom-out` / `egm-comprehension` / …）——
否则 skill 会退化成「spawn general-purpose 让它先读人格文件」。

`claude plugin list` 报的 `Default agents/ folder is ignored because the manifest sets "agents"`
是 **文档明确说预期且无害**的警告（harnesses.md:86）——Claude 用 `.claude-plugin/agents/` 下的 adapter。

### Artifact 目录

EGM 默认把 `concepts_brief.md` / `design_draft.md` / review 报告写进工作目录。按 `docs/harnesses.md`
的 Artifact Directory 一节，在 **`~/.claude/CLAUDE.md`** 加一行（用户级，所有项目生效）：

```text
EGM artifact directory: .dev/docs
```

并在本仓 `.gitignore` 加 `.dev/`（EGM 产物不入库）。
同时在全局 CLAUDE.md 加了一段 `## EGM` 小节：命令前缀、产物落点、**「评审很重，别当日常 code review 替代品」**。

## 与现有 skill 栈的重叠（用哪条）

| EGM | 对应现有 | 判断 |
|-----|---------|------|
| `egm-brainstorm` | `superpowers:brainstorming` | 重叠，EGM 版多了 7 视角 shootdown |
| `egm-draft` | `agent-skills:spec-driven-development` | 重叠，EGM 版强制写 `docs/designs/` |
| `egm-review` | `code-review-canonical` + `agent-skills:code-reviewer` | **形态不同**：EGM 是 8+ 次零上下文 subagent 扇出，canonical 是同上下文评 |
| `egm-resolve` | `superpowers:receiving-code-review` | 重叠 |
| `egm-review-loop` | 无 | **增量**：自定义评审组 |
| `egm-bootstrap` | 无 | **增量**：递归代码库文档生成 |
| `egm-drift-report` | 无 | **增量**：文档 vs 代码漂移 |

⇒ 日常 code review 仍用 `code-review-canonical`（便宜）；**只有真的要评审一份设计文档**时才上 EGM。

这直接命中本机已记录的痛点 `agent-4-layer-boundary-vs-cc-2026-10-12`（**CC 子任务层调用率严重不足**）——
EGM 用流程强制扇出，是外部结构替我兜住这条纪律。

## 坑 / 注意

1. **命令必须带 `/egm:` 前缀**（README 明说 Claude Code 下用 `/egm:egm-brainstorm`）。
2. **评审很重**：5 阶段 × 8+ reviewer = 十几次 subagent 调用，每次全新上下文读文档 + rubric。
   `egm-review` 不是「顺手跑一下」的东西。
3. **reviewer 看不到 CLAUDE.md**（adapter 设 `omitClaudeMd: true`）⇒ 评审假设必须显式写进 criteria，
   否则 Goldfish 不知道自己该挑战什么。
4. **新 session 才生效**：plugin 的 skill/agent 列表在会话启动时生成，当前会话看不到 `/egm:*`。
5. `.dev/docs` 是**相对路径**（相对工作目录）；若解析到工作目录之外，EGM 会先问一次确认，
   **答案不保存** ⇒ 下个 session 会再问。

## 诚实边界

- 本轮**只读了** `architecture.md` / `harnesses.md` / `egm-review/SKILL.md` + 17 个 frontmatter，
  **没有实际跑过一次 `/egm:egm-review`** ⇒ 「能不能真跑通、评审质量如何」**未经实测**。
  首次实跑建议拿一份小设计文档试，别直接上生产设计。
- token 数字是 **frontmatter 字符数换算**，不是真实计费 token；Claude Code 对 description 有截断，
  实际常驻**大概率低于**此值。
- 装它**没有解决**本仓 `docs/` 目录的规范问题，只是提供了另一条产出路径。
