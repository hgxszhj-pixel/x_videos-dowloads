# 分档派三档地盘 (Code Tier Zoning)

> **起源**: 2026-09-13 采纳「五派」中的 **分档派**。
> **目的**: AI 编辑代码前先看档位 — 不同档位的处理方式天差地别。
> **核心问题**: 你 memory 里三条血泪(`Chrome 152 --user-data-dir`、`__xe_store__ → xe.course`、`D:/ vs /d/`)反复被 AI 重踩,因为没显式钉死档位。

---

## 三档定义

| 档位 | 范围 | AI 处理方式 |
|------|------|------------|
| 🟢 **自由档** | 数据结构、配置 schema、UI 文案、test fixture、辅助工具 | 写完跑 `bash scripts/track_quality.sh` 即可,不细审 |
| 🟡 **审查档** | 下载主流程、URL 解析、文件名规则、并发控制 | 必走 `code-reviewer` agent + `track_quality.sh` + 检查 PR diff |
| 🔴 **禁止档** | 平台 API endpoint、平台鉴权/cookie 注入、浏览器 flag、平台特定路径写法 | **不许 AI 改**;改前必读 `~/.claude/projects/-Users-hgxszhj-x-videos-dowloads/memory/MEMORY.md` 全部相关条目 |

## AI 编辑前自检流程

```
1. 定位要改的文件 → src/path/to/file.rs
2. 在本表查档位
3. 如果是 🟢: 直接改,跑 track_quality.sh
4. 如果是 🟡: 改完必须 dispatch code-reviewer agent,贴 PR diff
5. 如果是 🔴: STOP — 先 grep 全部相关 memory:
   grep -nE "<filename>|<keyword>" ~/.claude/projects/-Users-hgxszhj-x-videos-dowloads/memory/MEMORY.md
   读完血泪教训后才能动笔;改动必须在 commit message 里解释"为什么这次不会重蹈覆辙"
```

## 维护规则

- **升档/降档**: 提 issue 讨论,不要私自改;改本表需要 PR + maintainer review
- **新文件归类**: 默认 🟡 审查档;只有纯数据结构/文案才 🟢;涉及外部平台契约必 🔴
- **过时清理**: 半年未触发的 🔴 条款 → 重新评估是否还是禁止档(可能上游已修)

---

## Why / How to apply

**Why**: 你 memory 里反复出现的"AI 又踩我踩过的坑"问题,根因不是 AI 蠢,是**档位没显式钉死**。AI 看到 `src/platform/shanhu.rs` 不知道它是禁止档,跟看到 `src/types.rs` 一视同仁,自然重蹈覆辙。

**How to apply**: 任何 AI 编辑任务,**第一步永远是 grep 本表 + grep MEMORY.md**,而不是直接读文件读代码。
